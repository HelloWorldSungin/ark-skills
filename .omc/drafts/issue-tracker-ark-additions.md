## AI-disclaimer convention

Every AI-authored comment on a GitHub issue — progress update, lifecycle
label move, close-out, discovered-work filing — starts with this line before
any other content:

```
> *This was generated by AI.*
```

This applies uniformly across all four proactive behaviors below and to any
other automated issue interaction (consultant epic filing, mattpocock
`/to-issues` / `/triage` output where it posts comments).

## The four proactive behaviors

1. **Progress comments on the working issue.** While actively working an
   issue, post periodic progress comments (not on every tool call — at
   meaningful checkpoints: plan settled, phase complete, blocker hit) via
   `gh issue comment <n> --body "..."`. Each comment carries the AI-disclaimer
   line first.

2. **Lifecycle label moves + close-out comments.** As an issue moves through
   the triage flow (`needs-triage` → `needs-info` ⇄ reporter →
   `ready-for-agent`/`ready-for-human` → closed), update labels with
   `gh issue edit <n> --add-label ... --remove-label ...` and post a
   close-out comment summarizing the outcome before `gh issue close <n>`.
   Epics get the same treatment: check off children in the epic body as they
   close, close-out comment when all children are done.

3. **Consultant-filed epics/children.** When the `ark-consult` skill (Phase
   4) files an epic from a triage conversation, it creates the parent issue
   with label `epic` plus a component label, and either files children
   directly (`gh issue create` with `story`/`task` labels, "Part of #NNN" in
   the body) or delegates child-cutting to mattpocock `/to-issues` per the
   Phase-3.4 validated contract. The consultant itself never does
   post-handoff orchestration — filing the epic/children is the last step
   before handoff.

4. **Discovered-work filing.** When work in progress surfaces a new,
   separable problem (not the thing currently being worked), file it as its
   own issue with `needs-triage` rather than silently expanding the current
   issue's scope. Cross-reference back to the discovering issue in the body
   ("Discovered while working on #NNN").

## Dual-write rule (OKF bundle `log.md`)

Every progress comment posted under behavior (1) is also appended to the
relevant OKF bundle's `log.md` (see `skills/vault/SKILL.md`, Phase 4.2) in the
same turn — the GitHub comment is the durable, queryable record; the
`log.md` entry keeps the vault's session-adjacent log continuous for
NotebookLM sync. Format: a short line with the issue number, a one-line
summary, and a link back to the GitHub comment (`gh issue view <n> --json url
--jq .url` for the permalink). This is a dual-write, not a migration — the
GitHub comment is authoritative; `log.md` is a synced mirror.
